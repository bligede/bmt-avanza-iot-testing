# hrv-001: Honda HR-V capture, recovered 20 Sep 2026

The only recording of the HR-V bus, pulled off the device flash three
weeks after the run, before the device was reflashed for anything else.

| | |
|---|---|

| Recorded by | firmware `2bcaabe`, unit id still `AVANZA-TEST-01` |
| Bitrate | 500 kbps, listen-only |

| Files | `captures/device-2026-09-20/can-000.log` … `can-033.log`, 8,786,358 B |

`captures/` is git-ignored: these files live on the work machine and need a
backup elsewhere. They cannot be recreated.

## What the recording contains

One continuous run. `millis()` climbs from 35,816 to 239,050 without a
restart, across all 34 segments: **3 min 23 s**, 180,416 frames, ~888 frames/s.

**The last 9.4 s are not vehicle data.** At 229.6 s the bus emits a burst of
39 identifiers never seen before, including extended and RTR frames with
all-zero payloads. Before that moment the recording holds **exactly 40
identifiers**, which is the number the dashboard displayed during the run
(photo of 16:06). The burst is the signature of the connector being unplugged.

So the evidence splits cleanly:

| Window | Frames | Identifiers | Use |
|---|---|---|---|
| 35.8 s → 229.6 s | 174,273 | 40 | **the vehicle** |
| 229.6 s → 239.1 s | 6,143 | 77 | disconnection noise, ignore |

`hrv-001.csv` contains the first window only. The raw logs keep both: raw
evidence is never edited (D-015), it is cut at the point of use.

## Integrity

- Every file's byte count matched the size the device reported.
- Every line parses; 61 lines (0.03%) are RTR frames printed with eight zero
  bytes, which is how the logger writes them, not corruption.
- No zero-byte padding anywhere.
- Two files were downloaded a second time; both SHA-256 digests matched.

### The serial console corrupts bulk transfers

First attempt used the console (`cat` over USB serial at 115200). The result
was **larger** than the original: `can-000.log` arrived as 286,184 B against
262,191 B on the device, padded with runs of zero bytes and duplicated
half-lines. The same duplication appears in the boot log, where one
`WIFI CONNECTED` line repeats seventeen times, and it silently ate a digit of
the device's own IP address (`192.168.100.4` for `.41`).

USB serial has no retransmission. **Do not pull evidence through it.** The
corrupt files are kept at `captures/serial-corrupt/` as the demonstration.
`tools/fetch_captures.py` (HTTP) is the supported path; `tools/pull_captures.py`
exists only for a device with no WiFi, and it size-checks every file.

## What this data can and cannot answer

**Can:** which identifiers the HR-V bus carries, their cycle times, which
bytes move, which byte is a rolling counter or a checksum. That is the survey
stage of `cansub-reverse-engineering`, and it can run today.

**Cannot:** what any value means. There is no reference series to correlate
against. GNSS had no fix (antenna fault, see the run photos), and OBD-II PID
polling is out of the question on a listen-only device. The recording also has
no `boot_epoch` header, because that came with `fd386ba`, so its timeline is
relative seconds, not wall clock.

The missing piece is a **video of the instrument cluster** on the next run,
which the skill's VISION mode reads into a reference series. Until then, any
signal claim about this data is a guess.

The dashboard photo of the same day shows odometer 069620 km, trip A 1459.6 km
and 29 °C. Those values were searched for across the ten payloads visible in
the screenshots and not found, which proves nothing either way; the full search
over all 40 identifiers is now possible against `hrv-001.csv`.
